# Phase 1 plan — Strava → Supabase on Cloudflare Workers

Source brief: Notion "Strava Training Analyzer" (Personal / Projects).
Revised after a plan review on 2026-10-06.

## Decisions

- **Hosting:** Cloudflare Workers, cron every 15 minutes. Free plan is sufficient: Strava's
  daily read limit (1,000) is the bottleneck, not Cloudflare's 50 subrequests per invocation.
- **OAuth:** one-time local script (Strava callback domain `localhost`). No public auth routes.
  The script verifies the OAuth `state`, the athlete ID, and that `read`, `activity:read_all`
  and `profile:read_all` (needed by `/athlete/zones`) were all granted.
- **Security:** RLS on every table with no policies; anon/authenticated grants revoked.
- **Data pulled for every run:** list summary + detailed view (laps, splits, best efforts,
  description). Per-second streams only for runs flagged `streams_wanted`, stored gzipped in
  Supabase Storage — keeps the database well under the 500 MB free limit and halves backfill time.
- **Idempotency:** all writes are upserts keyed on the Strava activity ID.
- **Freshness:** new runs every cron run; full re-pull of the last 30 days once a day to catch
  renamed/edited/deleted runs.
- **Observability:** `sync_runs` log table and a token-protected `GET /status`.
- **Extras for Phase 2:** athlete HR zones, local start time, `workout_type`, all run sport types.
- **File naming:** dated names for docs/notes; code follows normal conventions.

## External limits (checked 2026-10-06)

- Strava read limit: 100 requests / 15 min, 1,000 / day; windows reset at :00/:15/:30/:45 and
  midnight UTC. Overall limit 200 / 15 min, 2,000 / day.
- Cloudflare Workers free plan: 50 subrequests per invocation; cron invocations up to 15 min wall time.
- Strava API Agreement (Nov 2024): no use of API data for AI/ML model *training*. Personal
  analysis is not training — re-read the current terms before wiring any AI analysis in Phase 2.

## Implementation notes (Step 4)

- Backfill cursor is a `before` timestamp, not a page number: runs added or deleted mid-backfill
  cannot shift pages and cause skips.
- Per invocation: 15 Strava requests, 2 list pages by default. Worst case ~28 subrequests
  including Supabase calls (free-plan limit 50; enforced by a test). Throughput is capped by
  Strava's daily limit either way.
- Risk to watch: the free plan's 10 ms CPU limit per invocation. Parsing two 200-activity pages
  plus ~12 details may exceed it. If deploys log "Exceeded CPU limit", lower
  `SYNC_MAX_LIST_PAGES` to 1 or move to the $5 paid plan.

## Implementation notes (Step 5)

- New-run check is hourly (not every 15 min) to save ~70 requests/day; a new run lands within
  about an hour. It also runs during the backfill, so runs recorded mid-backfill aren't missed.
- 30-day re-pull is daily and starts one day after the backfill finishes (no point re-fetching
  details that were just fetched). It re-fetches every detail in the window, since descriptions
  can change without the summary changing.
- A run changed to a non-run sport is treated as deleted; listing it again as a run restores it.
- Paging with `after` uses the page parameter, so it is correct whichever order Strava returns.

## Steps

0. Accounts & keys — Strava app, Supabase project, Cloudflare account.
1. Repo scaffold.
2. Schema migration.
3. Local OAuth script.
4. Backfill: run list pages, then detail view per run, within a per-invocation request budget;
   resumable from `sync_state`.
5. Incremental sync + daily 30-day re-pull; deletion detection.
6. `runs_overview` view + CSV export script (optional: Supabase MCP for querying from Claude).
7. Tests (token refresh, budget/backoff, resume, upserts), `/status`, deploy, watch the backfill.
